## 1. 轻档：修 CLI 参数解析 bug

**对齐**：`--config` 缺少参数时当前会静默使用默认值，用户以为配置已加载。验收例子：

1. `--config` 缺参数时返回码 2，并输出用法提示。
2. `--config path` 正常读取指定文件。
3. 不带 `--config` 时保持原默认行为。

需求明确，未使用 grilling。

**调查事实与根因**：不建任务文件；先复现，再确定修复点。

- 根因依据：`app --config` 的失败用例显示缺参分支落入默认值 → 参数解析器未区分“未提供选项”和“提供选项但缺少值” → 在解析分支返回用法错误。
- 回归测试：先新增缺参测试并确认修复前失败，再实现修复并确认测试通过；同时保留正常路径和默认行为测试。

**设计充分性**：现有 SPEC 的 CLI 参数契约已经明确，无需新增设计。

**拆分**：单任务。参数解析、错误信息和测试同属一个可独立交付的 CLI 修复。

**分档**：轻档。不涉及外部写、权限、数据迁移、对外契约、跨模块或交接。

**分支**：`fix/<tool>/t-18-config-arg`，从 `develop` 创建。

**技能确认**：询问是否启用 ponytail，用户选择 `full`。

**实现与验证**：

```text

app --config             # 返回码 2，输出用法
app --config ./a.yaml    # 正常读取
```

**交付**：回复先列 3 列缺口摘要，再写变更与证据；一条提交，正文写证据；`TASK.md` 一行。

## 2. 完整档：接入新的外部邮件 API

**对齐**：新增外部邮件发送能力，涉及真实外部写、凭据、对外契约和跨模块。验收例子：

1. 使用测试账号发送一封邮件，外部写调用数为 1。
2. 凭据缺失时返回明确错误，不发起外部写。
3. 外部超时后不自动重试，保留结果未知状态和证据。
4. 重复执行同一请求不产生第二封邮件。
5. 现有 CLI 行为不变。

需求涉及外部写和凭据，先用 grilling 澄清了幂等、超时和测试账号边界。

**设计充分性**：现有 SPEC 已明确邮件发送契约、凭据和错误语义；本任务补充超时未知状态的处理，已回写 SPEC。

**拆分**：单任务。适配器、凭据、幂等和错误分类共享同一对外契约，拆分会产生不可交付中间态。

**分档**：完整档。命中外部写、权限/凭据、对外契约、跨模块。

**分支**：`feat/<tool>/t-19-mail-api`，从 `develop` 创建；worktree 位于 `../<repo>-wt/t-19-mail-api/`。

**计划**（任务文件 `tasks/2026-10-22-t-19-mail-api.md`）：

- 步骤：适配器接口 → 凭据读取 → 幂等键 → 错误分类 → 集成测试。
- 风险：真实外部写不可回滚；超时结果未知。
- 第一性原理检查：目标是可靠地执行一次邮件发送；不可变约束是真实写不可回滚、超时结果可能未知；关键假设是提供方支持幂等键；由此推导为单次调用、写前校验、持久化幂等键，不引入自动重试。

## 3. 拆分：一轮需求拆成多个任务

**对齐**：一轮需求包含三项能力：列表项高亮样式调整、批量删除、自定义分类。验收例子按能力分组，共 8 条。

## 4. 重大决定：只暂停受影响范围

**场景**：现有 SPEC 只要求“提供搜索”，但本地索引与托管搜索都会改变核心架构、持续费用和数据边界，且权威来源尚未决定采用哪一种。该事项同时满足“尚未确定”和“影响重大”。

**调查**：Agent 先核对数据规模、离线要求、预算、现有依赖和可逆性，把资料中的结论标为事实、推断或假设；不先写实现，也不要求开发者代查事实。

**决策包**：

- 待决定事项：本地索引或托管搜索。
- 已知事实与未知项：本地索引满足离线要求；托管方案的持续费用和数据驻留仍未知。
- 真实选项与取舍：本地索引增加客户端体积；托管搜索增加外部依赖和持续费用。
- 推荐：在数据驻留与预算确认前优先本地索引；推荐不等于已决定。
- 暂停范围：只暂停搜索存储适配器和部署设计。
- 恢复条件：开发者确认技术路线，或补充新的硬约束使答案唯一。

**并行**：与搜索路线无关的 CLI 参数修复已证明不依赖该决定，可以继续；不能证明独立的搜索任务记为 `进行中（待决定）`。普通命名和局部可逆实现不触发该门。

## 5. 轻档设计验证：结论不足也不能强行成功

**命题**：本地全文索引在目标低配设备上能否于 300 ms 内完成 10 万条记录查询。该事实会影响搜索架构；现有契约、源码和可信资料没有目标设备数据，直接完成正式索引实现的返工成本更高，因此创建设计验证任务。

**分档**：设计验证类型 + 轻档。实验只用本地虚构数据，限时半天，无外部写、不改 SPEC、不跨模块；“设计验证”类型不自动升级完整档。

**预声明**：

- 最小充分证据：目标设备上连续 30 次代表性查询，P95 ≤ 300 ms 为支持，P95 > 300 ms 为否定；没有目标设备结果则为结论不足。
- 有界影响：只检查搜索索引适配器和依赖该性能结论的任务；CLI 参数修复和导入格式任务继续。
- 预算与停止：半天；得到目标设备结果或达到时限立即停止，不自动追加下一轮。
- 代码处置：临时基准代码默认删除；若需长期复现，转为受测试的基准脚本并写明运行边界。

**结果**：当前只有开发机结果，达到预算后无法取得目标设备，结论为“结论不足”。验证任务本身按预定预算和步骤完成，但搜索架构仍保持 `进行中（待决定）`；不得把开发机通过写成目标设备已支持，也不得自动再做一轮实验。

## 6. 运行责任：何时创建 RUNBOOK

### 6.1 个人新建纯库

开发者确认采用 `独立开发 + 不运行`。仓库提供构建、测试和发布包说明，但不负责部署、启停、持久数据或恢复，因此不创建运行手册；`SPEC.md` 记录“不运行”及原因。没有空的 `docs/RUNBOOK.md`。

### 6.2 个人项目首次持续运行

项目准备向真实用户提供长期服务，运行责任从“不运行”变为“持续运行”，属于重大且尚未确定的决定。Agent 先调查现有代码和基础设施，向开发者提交环境、公开访问范围、运行账号、外部服务与费用、持久数据、可接受停机与数据损失、迁移、回滚、备份恢复、健康检查和告警的决策包。

开发者确认后：

- `SPEC.md` 写运行形态、环境/数据边界、可用性与恢复目标、失败语义、责任归属，以及运行手册路径。
- `docs/RUNBOOK.md` 写已验证的安装、配置、部署、迁移、回滚、健康检查、备份恢复和故障步骤；每一步有检查点、停止条件和升级路径。
- 如果项目已有 `OPERATIONS.md`，沿用该文件并由 SPEC 链接，不复制第二份 RUNBOOK。
- Agent 可以自主编写本地脚本、测试和文档，但真实部署、发布、迁移、恢复或生产配置修改仍需明确目标与操作授权。
